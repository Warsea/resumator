1. The mental model

JavaFX is a retained-mode, object-oriented desktop UI toolkit. You build a tree of Java objects (nodes), hand the tree to the framework, and it draws it and dispatches events. Unlike React, there is no virtual DOM and no re-render: you hold references to node objects and mutate them directly (like document.getElementById(...).textContent = ..., or like Tkinter's label.config(text=...)).

Closest analogy: JavaFX feels like Tkinter with a much better layout system and real CSS. There is no state-driven re-rendering. If data changes, you rebuild or update the relevant nodes. In Resumetor the profile page simply calls loadData(), which clears the container and rebuilds every card from the database.

3. Build system: Maven and the module system

3.1 pom.xml — your package.json

  • <dependencies> → dependencies. Maven downloads jars into ~/.m2. Key ones here: javafx-controls, ikonli-* (icon fonts), sqlite-jdbc, jackson-databind (JSON), poi-ooxml (DOCX), pdfbox (PDF), dotenv-java.
  • maven-compiler-plugin with <release>21</release> sets the Java version.
  • javafx-maven-plugin with <mainClass>app.resumetor.App</mainClass> makes mvn javafx:run work (like an npm run dev script). It handles the JavaFX module path for you.
Commandnpm analogy
mvn clean compiletsc (type-check/compile)
mvn javafx:runnpm run dev
mvn cleanrm -rf dist

Maven's standard layout is mandatory: Java in src/main/java, non-code files in src/main/resources. Resources are loaded off the classpath, e.g. getClass().getResourceAsStream("/db/schema.sql").

3.2 module-info.java

module app.resumetor {
    requires javafx.controls;      // UI widgets
    requires java.sql;             // JDBC
    requires java.desktop;         // BufferedImage (PDF preview)
    requires com.fasterxml.jackson.databind;
    requires org.apache.pdfbox;
    ...
    exports app.resumetor;
}

Java 9+ modules are an extra visibility layer: your code can only use a library if you requires it. Think of it as an explicit allow-list of imports at the package level. If you add a new library and get "package X is not visible", you almost certainly forgot a requires line here. (This is what bit us when the PDF preview needed java.desktop.)

4. How the app starts

public class App extends Application {
    public void init()            { DatabaseManager.getInstance().getConnection(); }  // background thread
    public void start(Stage stage) {                                                   // JavaFX thread
        SceneManager.setPrimaryStage(stage);
        Profile profile = new ProfileDao().getProfile();
        if (profile == null) SceneManager.showOnboarding();
        else                 SceneManager.showMainApp();
        stage.show();
    }
    public static void main(String[] a) { launch(a); }
}

Lifecycle: main() → launch() boots the toolkit and creates the JavaFX Application Thread → init() (setup, no UI yet) → start(Stage) (build UI; you are handed the primary window) → the event loop runs until the window closes → stop().

Boot sequence in Resumetor:

App.init()
  └─ DatabaseManager.getInstance()
        ├─ creates ./data/ folder
        ├─ opens jdbc:sqlite:data/resumetor.db
        └─ runs every statement in /db/schema.sql  (CREATE TABLE IF NOT EXISTS ...)
App.start(stage)
  └─ ProfileDao.getProfile() == null ?
        yes → SceneManager.showOnboarding()  → OnboardingLayout   (first run)
        no  → SceneManager.showMainApp()     → MainLayout         (normal run)

SceneManager is a tiny static "router for whole screens": it creates a Scene around a root node, attaches style.css, and swaps it onto the stage. Think of it as switching between /onboarding and /app.

Schema migrations: there is no migration tool. Because the schema uses CREATE TABLE IF NOT EXISTS, new tables (like profile_link) appear automatically on next launch, but changing columns of an existing table would require deleting data/resumetor.db or writing ALTER TABLE yourself.

Sizing and growth

HBox.setHgrow(spacer, Priority.ALWAYS);   // like  flex: 1  /  margin-left:auto
VBox.setVgrow(area,  Priority.ALWAYS);    // fill remaining vertical space
box.setPadding(new Insets(20));           // padding

The "spacer" trick used all over the code (an empty Region with Priority.ALWAYS) pushes the Edit/Delete buttons to the right edge of a row.

Building UI in code (no FXML)

JavaFX supports XML (.fxml) layouts, but this project builds everything in Java. It reads like JSX without the tags:

Label title = new Label("My Career Profile");
title.setStyle("-fx-font-size: 28px; -fx-font-weight: bold;");
container.getChildren().add(title);          // append to the parent

getChildren() is an observable list: adding/removing from it updates the screen immediately. getChildren().setAll(x) replaces everything, which is how the page content is swapped.

6. Layout classes as "components"; navigation

There is no component API like React. The convention here is: subclass a container and build children in the constructor.

public class SettingsLayout extends ScrollPane {          // "component" = a ScrollPane
    private final VBox container;
    public SettingsLayout() {
        container = new VBox(20);
        this.setContent(container);
        this.setFitToWidth(true);
        this.getStyleClass().add("main-content");         // CSS class
        buildUi();                                         // creates the child nodes
    }
}

Navigation = swap the center node

// MainLayout.java
public void setMainContent(Node node) {
    mainContent.getChildren().clear();
    mainContent.getChildren().add(node);
}
newAppBtn.setOnAction(e -> setMainContent(new NewApplicationLayout()));
profileBtn.setOnAction(e -> setMainContent(new ProfileDashboardLayout()));

That is the whole "router". Each click creates a fresh page object (so data is re-read from the DB). Child screens find the parent shell with getScene().getRoot() instanceof MainLayout (Java 16+ pattern matching), then call setMainContent or refreshApplications().

7. Styling with JavaFX CSS

JavaFX CSS looks like web CSS but with -fx- prefixed properties and a smaller selector set. The theme lives in resources/css/style.css and is attached once to the Scene/root.

.root {                                   /* like :root */
    -fx-font-family: "Segoe UI", "Inter", sans-serif;
    -bg-color: #F7F7F5;                   /* "looked-up colors" = CSS variables */
    -accent-primary: #4F46E5;
    -panel-bg: #FFFFFF;
}
.sidebar { -fx-background-color: -panel-bg; }   /* usage = var(--panel-bg) */
  • Variables: any -name: value declared in .root can be referenced as -name (no var()).
  • Classes: node.getStyleClass().add("btn") ↔ class="btn". The code also uses inline styles: node.setStyle("-fx-font-weight: bold;").
  • Common properties: -fx-background-color, -fx-background-radius, -fx-border-color, -fx-padding, -fx-text-fill (text colour, not color), -fx-font-size.
  • Icons: new FontIcon("fth-plus") from Ikonli; the fth- prefix is the Feather pack. A wrong prefix (ft-) caused an early crash.

8. Events, dialogs and forms

Events

Button addBtn = new Button("Add Skill");
addBtn.setOnAction(e -> openEntryDialog("Skills", null));

A lambda (e -> ...) is the same idea as a TypeScript arrow function. Variables captured by a lambda must be effectively final (never reassigned) — which is why you see one-element arrays or helper variables in a few spots.

Forms

Inputs are TextField (one line) and TextArea (multi-line). There is no two-way binding by default; you read values when the user confirms: nameField.getText().

Dialogs: modal and blocking

Dialog<ButtonType> dialog = new Dialog<>();
dialog.getDialogPane().getButtonTypes().addAll(ButtonType.OK, ButtonType.CANCEL);
dialog.getDialogPane().setContent(grid);                 // any Node
Optional<ButtonType> result = dialog.showAndWait();     // BLOCKS until closed
if (result.isPresent() && result.get() == ButtonType.OK) {
    // read fields, save, then loadData() to rebuild the page
}

showAndWait() is like await prompt(): the code after it runs when the user closes the dialog. Optional is Java's "maybe a value" (instead of null/undefined).

Add vs. edit share one dialog. openEntryDialog(section, item) receives null for "add" or the existing object for "edit". On save, CareerDao.saveX() inserts when id == null and updates otherwise — a manual "upsert".

The refresh pattern

private void loadData() {
    container.getChildren().clear();           // throw away the old nodes
    container.getChildren().add(buildBasicInfoSection(profileDao.getProfile()));
    container.getChildren().add(buildSection("Experience", "Add Experience"));
    ...                                        // rebuilt from the DB every time
}

Every mutation ends with loadData(). It is the manual equivalent of "state changed → re-render".

9. Threading: the one rule you must learn

Rule: only the JavaFX Application Thread may touch UI nodes, and it must never block (a long operation freezes the window). Anything slow — HTTP, big DB work, PDF rendering — goes on another thread, and the result is handed back with Platform.runLater(...).

Think of it as Node's single event loop, except that Java has real threads, so you must hop back to the UI thread explicitly. Tkinter has the identical rule (root.after / queue).

// GeneratedApplicationLayout.createLoadingTab
future.thenAccept(content -> Platform.runLater(() -> {      // hop back to UI thread
    tab.setContent(viewFactory.apply(content));              // safe to touch nodes now
})).exceptionally(ex -> {                                    // like .catch()
    Platform.runLater(() -> tab.setContent(errorLabel(...)));
    return null;
});

CompletableFuture<T> ≈ Promise<T>:

JavaTypeScript
future.thenApply(x -> y).then(x => y)
future.thenCompose(x -> otherFuture).then(x => otherPromise) (flattens)
a.thenCombine(b, (x,y) -> ...)Promise.all([a,b]).then(([x,y]) => ...)
future.thenAccept(x -> ...).then(x => { ... }) (no return)
future.exceptionally(ex -> ...).catch(ex => ...)
CompletableFuture.supplyAsync(() -> ...)new Promise(...) run off-thread

There is no async/await in Java; everything is chains of thenX.

10. The data layer

10.1 Models (model/)

Plain classes: private fields, public getters/setters. They are what interface Experience { company: string; ... } would be, but with boilerplate.

public class Skill {
    private Integer id;           // Integer (boxed) so it can be null = "not saved yet"
    private String name;
    private String proficiency;   // optional: just null/empty
    public Integer getId() { return id; }
    public void setId(Integer id) { this.id = id; }
    ...
}

Models: Profile, ProfileLink, Experience, Project, Education, Skill, JobApplication (an application with its generated documents attached).

10.2 SQLite + JDBC

SQLite is a single-file database (data/resumetor.db). JDBC is Java's standard SQL API — low-level, like pg or sqlite3, with no ORM.

String sql = "UPDATE skill SET name = ?, proficiency = ? WHERE id = ?";
try (Connection conn = DatabaseManager.getInstance().getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, s.getName());              // 1-based parameter index!
    ps.setString(2, s.getProficiency());
    ps.setInt(3, s.getId());
    ps.executeUpdate();                        // INSERT/UPDATE/DELETE
} catch (SQLException ex) { ex.printStackTrace(); }

// Reading:
try (ResultSet rs = stmt.executeQuery("SELECT * FROM skill")) {
    while (rs.next()) { s.setName(rs.getString("name")); ... }
}
  • try (...) { } is try-with-resources: auto-closes like Python's with.
  • ? placeholders (PreparedStatement) prevent SQL injection. Never concatenate user input into SQL.
  • SQLException is a checked exception: the compiler forces you to catch or declare it.

11. The AI layer

11.1 OpenRouterLLMService (ai/)

Wraps one HTTP endpoint: POST https://openrouter.ai/api/v1/chat/completions using Java's built-in java.net.http.HttpClient (like fetch). It builds the JSON body with Jackson's ObjectMapper (like JSON.stringify) and returns a CompletableFuture<String> with the model's text, parsed from choices[0].message.content. A jsonMode flag adds response_format: json_object so the model must return valid JSON.

The API key and model come from Config.get("OPENROUTER_API_KEY") / Config.get("AI_MODEL", default), which checks .env first and then real environment variables.

11.2 AiService (service/)

Each method builds a system prompt + user prompt and calls the LLM:

MethodOutput formatPurpose
analyzeJob(rawText)JSONExtract title, company, required skills, keywords...
matchProfileToJob(analysis)JSON of paragraphsFit report: strong/partial/missing, keywords, advice
generateResume(analysis, match)JSONSummary, skills, experience bullets, project bullets
generateCoverLetter(...)plain textThe letter body
generateEmail(analysis)plain textShort P.A.S. (Problem-Agitate-Solve) email

Prompts are string constants. Asking for strict JSON with a documented schema lets the app turn model output into proper layouts rather than showing raw text.

11.3 PiiSanitizer (security/) — privacy by design

The profile sent to the model contains placeholders ([NAME], [EMAIL], [PHONE], ...) instead of real contact data. When the output comes back, injectRealPii() swaps the real values in locally. Experience, projects and skills are sent because the model needs them to tailor the text; your identity and contact details never leave the machine.

11.4 JsonText (util/)

LLMs sometimes wrap JSON in markdown fences or add chatter. JsonText.parse() strips fences, slices from the first { to the last } and parses with Jackson, returning null on failure. humanize("missingRequirements") returns "Missing Requirements" for headings.

12. Documents: formatting, export and preview

One intermediate format feeds everything — a tiny markup ("markup" in the code):

# John Doe                         ← name (centred)
Software Engineer                  ← header lines (centred)
john@x.com | LinkedIn: https://... 

## Experience                      ← section heading (uppercase, underlined)
### Backend Engineer | Acme        ← entry heading (bold)
- Built X that improved Y          ← bullet
ClassRole
DocumentFormatterLLM JSON → markup. Adds the header from the saved Profile + links and the Education section straight from the database (facts are not left to the AI). Falls back gracefully if the model returned non-JSON.
PdfExportermarkup → PDF using Apache PDFBox: word-wrap, page breaks, centred header, section rules, standard fonts only (ATS-safe). build() returns the in-memory document; export() saves it.

In-app PDF preview

JavaFX has no PDF widget. The trick used here: build the PDF in memory with PdfExporter.build(), render every page to a BufferedImage with PDFBox's PDFRenderer, convert to a JavaFX WritableImage, and show it in an ImageView. Because the preview is the exported PDF, what you see is exactly what you save. Rendering runs on a background thread (supplyAsync) and the images are added to the UI via Platform.runLater. The "Edit Text" toggle swaps in a TextArea with the markup; switching back re-renders.

16. Known rough edges and exercises

Things worth knowing about this codebase

  • Shared connection. DAOs use try-with-resources on a shared Connection, which closes it; DatabaseManager.getConnection() silently reopens it. It works for a single-user desktop app but is not how you would do it in production (use a pool or open per call deliberately).
  • Concurrency. Several background threads save documents at the same time on the shared connection; SQLite serialises writes, but a proper design would use one writer thread or a pool.
  • Vault import is a TODO and the unused tables are placeholders.
  • No automated tests and no DB migrations.
  • Failed AI calls currently show the error in the tab; there is no retry button.

Exercises (in increasing difficulty)

  1. Change the accent colour in style.css (-accent-primary) and run the app.
  2. Add a "Location" field to Profile: update schema.sql (delete the DB), the model, ProfileDao, and the edit dialog.
  3. Add a "Regenerate" button to the results screen that reruns just the email future.
  4. Implement VaultManager.importVault using Jackson's TypeReference and the DAO save methods.
  5. Add a dark-mode toggle in SettingsLayout that swaps the stylesheet on the Scene.
  6. Move the DB connection to a per-call open/close and add a tiny single-thread executor for writes.

Mental checklist when adding a feature

  1. Model → add/extend a class in model/ and a table/column in schema.sql.
  2. DAO → SQL in repository/ (parameterised).
  3. Service (if AI or business logic is involved) → service/.
  4. UI → build nodes in a controller/ class; wire setOnAction.
  5. Slow work? → CompletableFuture + Platform.runLater.
